# 힐끔(Glance) 요구사항 정리

## 1. 프로젝트 개요

- 서비스명: 힐끔 (GLANCE)
- 목적: 특정 지역에서 지금 올라오는 스레드를 지도와 피드로 빠르게 확인하고 작성할 수 있는 서비스
- 초기 플랫폼: 모바일 웹뷰 중심
- 기준 해상도
  - 모바일: 360px
  - 웹: 1920px
- 디바이스 대응 방침
  - 모바일과 태블릿 breakpoint를 구분해서 대응
  - 실제 구현 우선순위는 모바일 웹뷰 기준

## 2. 반응형 기준

### 반응형 전략

- Next.js 기반 웹뷰(PWA)를 전제로 모바일 우선 방식으로 설계
- 기기명 기준이 아니라 레이아웃이 실제로 변하는 시점을 기준으로 breakpoint 적용
- 우선 대응 범위는 모바일과 태블릿
- 데스크톱은 주 사용 환경이 아니므로 확장 대응 수준으로 처리

### 권장 breakpoint

- 모바일: 0px ~ 767px
- 태블릿: 768px ~ 1023px
- 확장 화면: 1024px 이상

### 화면 설계 원칙

- 모바일은 360px 기준으로 UI 설계
- 태블릿에서는 여백, 카드 폭, 입력 폼 폭을 확장
- 지도 화면은 모바일에서 단일 레이아웃 우선 적용
- 태블릿에서는 필요 시 지도와 패널의 활용 폭을 넓히되 정보 밀도를 과하게 높이지 않음
- 큰 화면에서는 콘텐츠 최대 너비를 제한해 지나치게 퍼져 보이지 않도록 처리

### 구현 메모

- 기본 CSS 전략은 mobile-first로 구성
- 대표 breakpoint 기준 예시
  - `@media (min-width: 768px)`: 태블릿
  - `@media (min-width: 1024px)`: 확장 화면
- 주요 점검 대상
  - 지도 영역 높이와 하단 시트 배치
  - 피드 카드 폭과 텍스트 가독성
  - 글쓰기 폼의 입력 영역과 버튼 배치
  - 댓글 리스트 및 상세 화면의 세로 스크롤 사용성

### 반응형 토큰 초안

```css
:root {
  --bp-tablet: 768px;
  --bp-desktop: 1024px;

  --page-max-width: 640px;
  --page-padding-mobile: 16px;
  --page-padding-tablet: 24px;

  --bottom-nav-height: 64px;
  --header-height: 56px;
  --fab-size: 56px;

  --feed-card-radius: 16px;
  --sheet-radius: 20px 20px 0 0;
}

@media (min-width: 768px) {
  :root {
    --page-max-width: 860px;
    --page-padding-tablet: 32px;
  }
}

@media (min-width: 1024px) {
  :root {
    --page-max-width: 1024px;
  }
}
```

### Tailwind 사용 시 기준 예시

```ts
screens: {
  tablet: "768px",
  desktop: "1024px",
}
```

### 적용 원칙

- 모바일 기본 레이아웃에서 모든 화면을 먼저 설계
- 태블릿에서는 컴포넌트 크기보다 여백과 최대 폭을 먼저 확장
- 피드 카드, 상세 화면, 작성 폼은 `max-width`를 두어 가독성을 유지
- 지도 화면은 높이 확보가 중요하므로 좌우 분할보다 상하 구조를 우선 검토
- FAB, 하단 탭, 바텀시트 등 모바일 핵심 UI는 태블릿에서도 완전히 다른 패턴으로 바꾸기보다 확장형으로 유지

## 3. MVP 범위

### 포함

- 로그인 없이 서비스 진입 및 게시글 작성
- 서울 지역 중심 지도 화면
- 지도 내 스레드 마커 및 클러스터 표시
- 최신순 스레드 피드
- 스레드 상세 조회
- 좋아요 및 댓글 상호작용
- 지도/피드 양쪽에서 스레드 작성 진입
- 태그 기반 장소 표현

### 제외

- GPS 기반 현재 위치 수집
- 사진 첨부 기능

## 4. 정책 및 제약사항

### 위치 정보

- 위치기반서비스 신고 이슈를 고려해 GPS를 가져오는 방식은 사용하지 않음
- 장소는 태그 기반으로 확인할 수 있도록 설계
- "서버에 저장하지 않으면 괜찮은지" 여부는 별도 확인 필요

### 콘텐츠 작성

- 누구나 로그인 없이 게시글 작성 가능
- 사진 첨부는 지원하지 않음

### 지역 범위

- 초기 MVP는 한국 전체가 아니라 서울로 한정하여 진행
- 현재 핫한 지역 이름이 리스트 형태로 표시되는 방향 고려

## 5. 사용자 시나리오

### 4.1 로그인 / 계정

#### 목표

- 사용자는 로그인 없이 앱을 바로 사용하고 싶다
- 번거로운 가입 과정 없이 빠르게 서비스를 이용할 수 있어야 한다

#### 요구사항

- 별도 로그인 없이 서비스 진입 가능해야 함
- 누구나 게시글을 작성할 수 있어야 함

### 4.2 메인 홈화면: 지도

#### 목표

- 사용자는 지도에서 스레드 위치를 보고, 어디에서 어떤 이야기가 올라오는지 한눈에 파악하고 싶다

#### 요구사항

- 메인 지도는 서울 영역 기준으로 제공
- 최초 진입 시 지도는 저장된 스레드 좌표를 조회하는 용도로 사용되어야 함
- 지도에 스레드가 존재하면 각 스레드는 마커로 표시되어야 함
- 지도 새로고침 버튼은 마커 새로고침 기능을 제공해야 함
- 지도 새로고침 버튼을 누르면 새로 추가된 스레드 마커 데이터를 다시 불러와 지도에 그려야 함
- 사용자가 줌인/줌아웃한 상태에서 지도 새로고침 버튼을 누르면 초기 설정 줌 레벨로 돌아가야 함
- 사용자가 마커를 클릭하면 해당 스레드의 요약 정보가 표시되어야 함
- 여러 스레드 마커가 밀집한 경우 축소 시 클러스터로 묶이고, 스레드 개수가 숫자로 표시되어야 함
- 클러스터 숫자 표시는 최대 `+99` 기준으로 표현되어야 함
- 하나의 위치에 여러 게시글이 있을 경우 클릭 시 가장 최신 글이 우선 표시되어야 함
- 기본 화면에서는 조회만 가능하고, 별도 등록 액션을 눌렀을 때만 좌표 등록 플로우로 진입해야 함

#### 지도 액션 버튼

- 지도/피드 탭 버튼이 하단에 제공되어야 함
- 지도 화면에는 제보하기 버튼이 제공되어야 함
- 제보하기 버튼(`+`)을 눌렀을 때만 좌표 기반 스레드 등록 플로우로 진입해야 함

### 4.3 스레드 피드

#### 목표

- 사용자는 최신 스레드를 상단에서 보고 실시간으로 올라오는 글을 빠르게 확인하고 싶다

#### 요구사항

- 스레드 리스트 진입 시 최신 작성 순으로 정렬되어야 함
- 새로운 스레드가 생성되면 리스트 갱신 시 최상단에 표시되어야 함
- 사용자가 스크롤하면 추가 스레드가 로드되어야 함
- 리스트 상단에서 당겨서 새로고침할 수 있어야 함
- 초기에는 누적 데이터 중심으로 표시
- 이후 게시글이 많아지면 표시 기간을 줄이는 방향 고려

### 4.4 스레드 상세 / 상호작용

#### 목표

- 사용자는 스레드를 클릭해 상세 내용을 보고 글의 맥락과 다른 사람들의 반응을 확인하고 싶다

#### 요구사항

- 스레드 상세 화면에서 제목, 내용, 작성 시간이 표시되어야 함
- 좋아요 버튼 클릭 시 좋아요 수가 즉시 증가해야 함
- 이미 좋아요를 누른 상태에서 다시 누르면 취소되어야 함
- 댓글이 존재하면 등록순으로 표시되어야 함
- 댓글 작성 후 등록하면 리스트에 즉시 추가되어야 함

### 4.5 스레드 작성

#### 목표 1

- 사용자는 지도 또는 스레드 리스트 어디서든 빠르게 글을 작성하고 싶다

#### 요구사항

- 지도 화면에서 제보하기 버튼(`+`) 클릭 시 글 작성 화면 또는 좌표 등록 플로우로 이동해야 함
- 스레드 피드 화면에서 `+` 버튼 클릭 시 글 작성 화면으로 이동해야 함

#### 목표 2

- 사용자는 제목, 본문, 태그를 입력해 장소성과 맥락을 담은 글을 작성하고 싶다

#### 요구사항

- 제목 또는 본문이 50자 이상 입력되지 않으면 작성 완료 버튼이 활성화되지 않아야 함
- 작성 항목은 제목, 본문, 태그를 포함해야 함
- 태그는 장소를 표현하고 탐색하는 핵심 수단으로 사용해야 함

#### 목표 3

- 사용자는 글 작성 완료 후 바로 서비스에 반영되길 원한다

#### 요구사항

- 글 작성 완료 후 제출하면 지도에 마커가 생성되어야 함
- 글 작성 완료 후 리스트 갱신 시 해당 글이 최상단에 표시되어야 함

## 6. 태그 기반 장소 설계 메모

- GPS를 사용하지 않으므로 장소 식별은 태그 중심으로 설계
- 사용자는 글 작성 시 장소 관련 태그를 직접 입력할 수 있어야 함
- 태그를 통해 특정 지역/장소 단위로 스레드를 탐색할 수 있어야 함
- 지역 표현 방식은 서울 내 행정구/동/핫플레이스 기준 등으로 추가 기획 필요
- 태그 사용 방식과 장소 확인 UX는 별도 상세 기획 보완 필요

## 7. 화면별 핵심 기능 요약

### 홈 / 지도

- 네이버 지도 API 사용
- 서울 중심 지도 제공
- 초기 진입 시 저장된 좌표 조회 중심 화면
- 스레드 마커 표시
- 클러스터 표시
- 클러스터 숫자 최대 `+99` 표기
- 마커 클릭 시 최신 글 기준 요약 노출
- 지도 새로고침 버튼으로 마커 재조회
- 지도 새로고침 버튼으로 초기 줌 레벨 복귀
- 제보하기 버튼(`+`)으로만 좌표 등록 진입
- 하단 지도/피드 탭 제공

### 스레드 피드

- 최신순 정렬
- 무한 스크롤
- 당겨서 새로고침
- 태그 필터 제공
- 글쓰기 진입 버튼 제공

### 스레드 상세

- 제목 / 내용 / 작성 시간 표시
- 좋아요 토글
- 댓글 목록 / 댓글 작성

### 글쓰기

- 제목, 본문, 태그 입력
- 입력 조건 충족 시만 제출 가능
- 작성 완료 후 지도/피드에 즉시 반영
